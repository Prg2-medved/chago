# Design

## Context

Мотивация и scope описаны в proposal.md; наблюдаемый контракт — в specs/application-bootstrap/spec.md. В проекте пока есть SPEC.md, OpenSpec и локальный venv Python 3.12.7; исходников приложения и тестов нет. SPEC.md остаётся верхнеуровневым источником требований. Этот этап реализует только bootstrap: расширенный health (§20) и два сервиса полного MVP (§22) откладываются явно по запросу пользователя.

Design необходим из-за новых зависимостей FastAPI/Uvicorn и выбора единого способа запуска для локальной среды и контейнера. Сервер CPU-only, 15 ГиБ RAM; каркас не загружает модели и не резервирует ресурсы под них.

## Goals / Non-Goals

**Goals:** одинаковый HTTP-контракт локально и в контейнере, один процесс, небольшой набор зависимостей, понятные команды установки и тестирования.

**Non-Goals:** provider interfaces, repositories, service layers, dependency containers и заглушки будущих компонентов. Полный список функциональных исключений находится в proposal.md. Автономность runtime не требует реализации firewall или offline-установщика.

## Decisions

### 1. Минимальный пакет и Python 3.12

Использовать структуру, сокращённую из §21 SPEC.md:

```text
compose.yaml
.env.example
README.md
app/
  Dockerfile
  .dockerignore
  requirements.txt
  requirements-dev.txt
  app/
    __init__.py
    __main__.py
    main.py
    config.py
  tests/
    test_health.py
    test_config.py
```

Команды Python выполнять из внешнего каталога `app/`: запуск `python -m app`, тесты `python -m pytest`. Корневой Compose использует build context `./app`. Python 3.12 соответствует уже созданному локальному окружению. Не создавать packaging/build-tool инфраструктуру: requirements-файлов достаточно для приложения, которое не публикуется как библиотека. Альтернатива с src-layout и installable package пока не даёт нужного пользователю поведения.

### 2. FastAPI и один Uvicorn process

`main.py` содержит FastAPI app и GET /health. `__main__.py` читает конфигурацию и запускает Uvicorn одним worker, без reload. Health возвращает только status=ok, без probes и полей будущего индекса. Дополнительные frontend/API-docs страницы не нужны; отключить встроенные docs/redoc, чтобы не добавлять браузерные страницы с внешними assets.

Альтернатива — запуск непосредственно через CLI Uvicorn — потребовала бы отдельно согласовывать передачу APP_HOST/APP_PORT. Маленькая точка входа оставляет один способ запуска в README и Dockerfile.

### 3. Только две настройки окружения

Читать через стандартный `os.environ` APP_HOST (локально 127.0.0.1) и APP_PORT (8000), проверять порт как целое число 1–65535. Отдельный framework конфигурации или dotenv-loader не нужен. Локально переменные экспортируются средствами shell; файл .env автоматически Python-приложением не читается. README показывает команды для PowerShell и POSIX shell.

В Compose задавать внутри контейнера APP_HOST=0.0.0.0 и APP_PORT=8000. Корневой .env, созданный из .env.example, используется Compose для подстановки адреса/порта публикации: APP_HOST по умолчанию 127.0.0.1 и APP_PORT по умолчанию 8000 с отображением на контейнерный порт 8000. Для LAN оператор явно задаёт APP_HOST=0.0.0.0. В README различать адрес публикации на хосте и адрес прослушивания внутри контейнера. Без .env значения по умолчанию работают.

Настройки будущих моделей, Wiki.js, БД и reindex отсутствуют. Альтернатива с общим settings framework и неиспользуемыми параметрами увеличила бы scope.

### 4. Зависимости устанавливаются до runtime

Runtime: FastAPI и Uvicorn; development: pytest и HTTPX для FastAPI TestClient. requirements-dev.txt включает runtime requirements. При реализации зафиксировать совместимые проверенные версии; не устанавливать ML/CUDA-пакеты или дополнительные optional extras. Dockerfile на Python 3.12 slim устанавливает runtime requirements при сборке и запускает `python -m app`; entrypoint не вызывает pip и не скачивает ресурсы.

Один сервис app, один опубликованный порт, без томов и без изменения Compose Wiki.js. .dockerignore исключает локальное окружение, кэши и локальные env-файлы из build context. Альтернатива с установкой при старте нарушает offline runtime.

### 5. Проверять наблюдаемое поведение

Pytest проверяет HTTP 200/JSON /health, значения конфигурации по умолчанию, environment overrides и отказ для некорректного порта. TestClient не требует сетевого сервера. Дополнительно при реализации выполнить реальные smoke checks локального процесса и Compose, включая нестандартный порт.

Offline-проверка выполняется после установки/сборки: запуск и повторный запуск при отключённом внешнем доступе с сохранением loopback-доступа, затем запрос /health. Для контейнера допустим отдельный smoke run уже собранного образа с `--network none` и запрос через стандартную библиотеку Python внутри контейнера; штатный Compose остаётся с опубликованным портом. Не менять firewall хоста ради теста. Если среда не позволяет проверить Docker или отключить интернет, явно записать непроверенный критерий, не объявляя его выполненным.

## Risks / Trade-offs

- Разное значение bind address в контейнере и локально → фиксировать контейнерный 0.0.0.0:8000 и документировать host publication отдельно.
- Отсутствие интернета при первой установке → автономность гарантируется только после установки пакетов/сборки образа; это согласовано с §5 SPEC.md.
- Минимальный health может быть принят за готовность RAG → явно обозначить app-only health в README и не выводить фиктивные статусы зависимостей.
- Версии библиотек могут оказаться несовместимыми → закрепить версии при реализации после прохождения pytest и container smoke check.

## Migration Plan

Данных и существующего приложения для миграции нет. Установить зависимости локально либо собрать образ, выполнить проверки, запустить один app. Откат — остановить этот Compose project; существующая Wiki.js не затрагивается. Текущий change создаёт только документы; описанные действия выполняются отдельным apply-запросом.
