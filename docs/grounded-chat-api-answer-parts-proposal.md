# Предложение: составной ответ за один completion

Дата: 2026-10-22. Статус: **отклонено владельцем, не реализовано**.

Решение от 2026-10-22: эксперимент `parts` не реализуется; семантическое качество
генерации перенесено в post-MVP. Текст ниже сохранён как прежнее предложение,
не является действующим планом или запросом согласования. Актуальный проект
критериев — SPEC §27 и planning artifacts `grounded-chat-api`.
Change: `grounded-chat-api`, задача 7.2. Это проект поправок к planning artifacts,
а не новая принятая версия design или результат live-проверки.

## Основание и выбор

В [последнем tuning q01 review](grounded-chat-api-prompt-examples-q01-review-2026-10-22.json)
evidence полное в обоих режимах, validation_error=null, но оба verdicts — fail.
Generation-only опускает контроль маршрута и объявляет недостаточность без
названного пробела; end-to-end пропускает несколько фактов и придумывает пробел.
Это наблюдаемые generation failures, а не доказанная ошибка parser или retrieval.
Другие раскрытые cases и holdout для подготовки этого предложения не читались.

Текущий design §5 допускает один completion с `{kind, answer}`. Перестановка
этих двух полей или ещё одно словесное правило остаются совместимыми, но не
дают нового проверяемого представления полноты ответа. Grammar/JSON-schema mode
может ограничить синтаксис, однако у этого q01 синтаксическая проверка уже прошла.
Такая оптимизация сама по себе не проверит пропущенные факты, ложный пробел,
entailment citations или команду вне fences. Сейчас её не предлагается включать.

Предлагается один ограниченный эксперимент: модель выдаёт отдельные части
запрошенного ответа, а затем выбирает kind. У каждой части явно указаны предмет,
состояние подтверждения и готовый текст с citations. Backend проверяет
согласованность, объединяет тексты и применяет прежние validators. Гипотеза:
явное перечисление частей уменьшит пропуски и необоснованный выбор partial.
Преимущество над очередной редакцией prompt — возможность отдельно отклонять
формально несогласованные части и kind. Улучшение качества ещё не измерено.

## Предлагаемый внутренний протокол

Для содержательного ответа — единственный JSON object:

```json
{
  "parts": [
    {
      "aspect": "Где хранятся файлы",
      "status": "supported",
      "text": "Файлы сохраняются в /srv/archive. [chunk:aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa]"
    },
    {
      "aspect": "Кто администратор",
      "status": "missing",
      "text": "Администратор в переданных источниках не указан."
    }
  ],
  "kind": "partial"
}
```

Это вымышленный пример формата: ID допустим только при наличии соответствующего
fragment в текущем packed manifest. Данные примера не являются evidence.

- `aspect` — непустое краткое название части текущего вопроса. Для широкого вопроса
  модель выделяет основные факты по релевантному evidence, без списка required facts
  из evaluation. Backend не извлекает аспекты эвристикой и не подаёт expectations.
- `status` — ровно `supported`, `missing` или `conflict`.
- `text` — готовый непустой русский текст этой части. Все citations, включая обе
  стороны конфликта, пишет модель. `aspect` не публикуется как дополнительный факт.
- `supported` требует валидную citation внутри собственного text. Команды внутри
  text модель обязана писать дословно в fenced blocks с citation вне блока.
- `missing` называет конкретную запрошенную часть, для которой нет сведений.
  Это описание пробела без команд и содержательных утверждений об объекте;
  citations в этой части не допускаются: найденный fragment не доказывает отсутствие.
- `conflict` содержит оба варианта с citations как минимум двух различных packed
  chunk IDs. Наличие двух IDs — проверка структуры, не доказательство противоречия.
- `kind=answer` допустим только при непустом parts, где все части supported.
- `kind=partial` требует хотя бы одну supported/conflict часть и хотя бы одну
  missing/conflict часть. Ответ, состоящий только из missing, недопустим.
- Для `refuse` и `clarify` остаётся текущая форма `{kind, answer}`, без parts:
  стандартный отказ либо одно короткое уточнение без фактов. Текущие проверки
  этих ветвей сохраняются. Объект вопроса нельзя подставлять по похожему документу.

Порядок parts перед kind задаётся prompt. Без constrained decoding JSON parser
не может заставить модель генерировать ключи в таком порядке; это часть гипотезы,
а не гарантия исполнения. Лишние поля, дубли ключей, неверные типы и смешение
двух форм отклоняются. Старый `{kind, answer}` для answer/partial не принимается
как запасной путь: иначе эксперимент не проверяет новый протокол.

После проверок backend объединяет исходные `text` в порядке parts через `\n\n`,
без изменения их содержимого и без добавления citations. Полученный текст проходит
прежнюю проверку markers, source links и exact fenced blocks. Дополнительно каждая
supported/conflict часть проходит проверку citations самостоятельно: citation
соседней части не засчитывается. Подстановка номеров и source metadata остаётся
существующим механизмом только для явно указанных моделью markers.

Неверная структура, несогласованный kind, неизвестная citation или неверная команда
дают прежний безопасный fallback целиком, без повторного completion. Backend
не меняет kind/insufficient_context на основании найденных citations, не дополняет
факты и не переносит citations из соседней части. `insufficient_context` по-прежнему
определяется принятым kind, прошедшим проверки, а не исправляется после генерации.

## Что эксперимент не доказывает

Модель может не выделить обязательный аспект, выдумать missing, выбрать неверную
citation либо спрятать команду в обычном тексте. Структура этого не исключает.
Проверки kind ловят формальную несогласованность; они не оценивают достаточность
evidence по смыслу. Существование marker не доказывает entailment, а exact-code
validator по-прежнему не является универсальным детектором команд в прозе.
Все эти свойства остаются обязательными пунктами ручной приёмки, без снижения gate.

Новый JSON расходует часть прежнего лимита 768 output tokens. Дублировать полный
ответ и отдельный evidence ledger не предлагается: text частей и есть ответ.
Нельзя исключить обрезание до измерения. Неполный JSON скрывается прежним fallback;
увеличивать reserve/max_tokens или timeout для спасения эксперимента без решения
владельца нельзя. Новые зависимости, schema/grammar request options и runtime
flags в этот эксперимент не входят.

## Поправки к planning artifacts после согласования

1. `proposal.md`: уточнить один структурированный completion с частями ответа;
   публичный API, retrieval и критерии приёмки сохраняются.
2. `design.md` §5: заменить `{kind, answer}` для answer/partial описанным parts
   протоколом, правилами kind и объединением text; сохранить отдельные refuse/clarify.
   В §6 добавить проверку citations каждой содержательной части и полный fallback
   при ошибке любой части. В risks явно указать цену output tokens и ограничения
   проверки полноты, entailment/конфликтов и команд вне fences.
3. Delta spec: добавить requirement «Structured answer parts» с SHALL для схемы,
   локальных citations, kind consistency, объединения без добавления фактов/markers
   и fallback без retry. Добавить scenarios: complete parts; missing part;
   two-sided conflict; inconsistent kind; uncited part despite cited neighbour;
   exact fenced command; malformed/truncated parts; refuse/clarify separate form.
   Существующие требования о полноте фактов, citations, командах и live acceptance
   остаются обязательными.
4. `tasks.md`: добавить отдельные открытые задачи для реализации протокола,
   meaningful tests и обновления документации/harness diagnostics. Ранее принятые
   результаты не переписывать. После фактического изменения messages переоткрыть
   7.1 для новой ревизии; сейчас 7.1 остаётся принятой. 7.2–7.4 остаются открытыми.

Согласование этого документа разрешает сначала обновить эти четыре planning
artifacts по указанным правилам, проверить их согласованность и затем реализовать
описанный эксперимент. Модель, image, sampling, window, reserve, timeout и runtime
flags сохраняются закреплёнными. Любое дополнительное изменение требует отдельного
предложения.

## Объём реализации и проверка

Основные изменения ожидаются в `app/app/grounding.py` и
`app/tests/test_grounding.py`: typed parts, strict parsing, проверки частей,
объединение text и prompt на вымышленных fixtures. ChatService сохраняет один
completion и общий generation gate. Harness должен пользоваться тем же validator,
выдавать безопасные категории новых ошибок без raw invalid output и сохранять
существующие fingerprints/evidence IDs. Профильные tests охватят обе ветви схемы,
kind mismatch, missing-only, соседнюю citation, неизвестные/removed IDs, две стороны
конфликта, injection strings, точную команду и её искажения, truncation и отсутствие
второго completion. Обновляются docs формата и диагностических категорий.

Проверки выполняются последовательно:

1. Согласованные planning artifacts: OpenSpec strict validation, без отметок
   о реализации до выполнения проверок.
2. Grounding, chat API, evaluation и token-check tests, профильная mypy-проверка,
   diff check. Полный regression только при выявленном влиянии на другие компоненты.
3. Оператор: 7.1 на окончательных messages новой ревизии с тем же runtime. Старые
   2734/2734 не засчитываются для нового prompt.
4. Оператор: один tuning q01 в обоих режимах с наблюдением memory во время прогона,
   сохранением identity/settings, counts, timings и JSONL. Затем ручной review
   обязательных фактов, kind, каждой citation и команд. До изменения кода повторять
   прежний q01 не требуется. При uncertain generation — прежний ручной recovery,
   без retry; прежние memory snapshots не доказывают стабильность.
5. Если новый q01 снова fail — не запускать весь corpus автоматически и не снижать
   требования; вынести результат владельцу. Если pass — это только основание
   продолжить согласованную tuning-проверку, а не закрыть 7.2. Holdout не используется
   для настройки; финальная приёмка остаётся отдельной процедурой после фиксации
   реализации. Compose-проверка 7.3 по-прежнему обязательна отдельно.

## Решение владельца

Требуется согласовать замену внутреннего протокола в design §5 и описанные поправки
к proposal/spec/tasks до реализации. Основание — прямое указание пользователя
сначала согласовывать изменения design. До решения действующие planning artifacts,
runtime-код и prompt остаются прежними; новые live-прогоны не запрашиваются.
