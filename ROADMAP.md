# Chago RAG Roadmap

## Назначение

Этот roadmap описывает целевую последовательность развития локальной RAG-системы Chago — от базового приложения и локальной LLM до полностью автономного read-only RAG.

Roadmap намеренно не хранит статус выполнения и не требует регулярного обновления. Фактическое состояние реализации, активные задачи и завершённые изменения хранятся в OpenSpec.

Первые фундаментальные этапы также включены в roadmap, чтобы вся архитектурная последовательность проекта была видна в одном месте.

Роли документов:

```text
SPEC.md
→ верхнеуровневые требования к системе

ROADMAP.md
→ последовательность этапов развития и brief для каждого этапа

OpenSpec
→ конкретные proposal / design / spec / tasks и фактический статус реализации
```

---

## Как пользоваться roadmap

Каждый этап ниже содержит самостоятельный **Brief для OpenSpec**.

Когда нужно начать очередной этап:

1. Выбрать следующий этап по порядку, который ещё не реализован согласно OpenSpec.
2. Скопировать весь блок **«Brief для OpenSpec»** этого этапа.
3. Передать его Codex/OpenSpec с указанием создать соответствующий change через `$openspec-propose`.
4. Просмотреть созданные `proposal`, `design`, `spec` и `tasks` до начала реализации.
5. После согласования выполнить `$openspec-apply-change <change-name>`.
6. Выполнить реализацию и обязательно провести реальные проверки, предусмотренные `tasks.md`.
7. Отметить задачи `[x]` только после фактической проверки.
8. Когда выполнены все задачи, запустить `$openspec-archive-change <change-name>`.
9. Если OpenSpec предлагает синхронизацию delta specs, выбрать **синхронизировать и архивировать**.
10. Проверить итоговые specs:

```bash
openspec validate --all --strict
```

11. Проверить изменения Git:

```bash
git status --short
git diff
```

12. После успешной проверки сделать commit и push.

Для начала нового этапа не нужно придумывать новое ТЗ с нуля: достаточно взять соответствующий brief из этого файла. При необходимости OpenSpec детализирует его в `proposal`, `design`, `spec` и `tasks`.

## 1. `bootstrap-project`

### Brief для OpenSpec

Создать change `bootstrap-project`.

Цель: создать минимальную основу приложения, на которой будут строиться все последующие этапы RAG.

Нужно подготовить:

- FastAPI-приложение;
- минимальный `GET /health`;
- конфигурацию через environment variables;
- pytest;
- Dockerfile;
- Docker Compose;
- базовый README с командами запуска и проверки.

Приложение должно запускаться независимо от будущих LLM, Wiki.js, индекса и retrieval-компонентов.

На этом этапе не добавлять:

- LLM;
- embeddings;
- Wiki.js ingestion;
- БД индекса;
- retrieval;
- RAG API;
- Web UI;
- внешние очереди и вспомогательную инфраструктуру.

Результат этапа: есть минимальное работоспособное приложение с воспроизводимым локальным и контейнерным запуском, health-check и тестами.

## 2. `local-cpu-runtime`

### Brief для OpenSpec

Создать change `local-cpu-runtime`.

Цель: добавить полностью локальный CPU-only runtime для LLM, который будет использоваться будущим RAG.

Базовая модель:

```text
Qwen3-4B-Instruct-2507
```

Формат модели:

```text
GGUF
```

Runtime:

```text
llama.cpp / llama-server
```

Нужно обеспечить:

- один `llama-server` внутри Docker Compose;
- CPU-only запуск без зависимости от GPU/CUDA;
- локальный GGUF, который устанавливается вручную заранее;
- отсутствие runtime-загрузок модели из интернета;
- read-only bind mount GGUF;
- закреплённый image digest;
- внутренний доступ `app → llm`;
- отсутствие публикации LLM-порта наружу;
- `parallel=1`;
- CLI-проверки LLM health и completion;
- возможность менять model path и alias без изменения Python-кода;
- корректную ошибку при отсутствующем или некорректном GGUF;
- app-only режим;
- offline запуск и restart после предварительной установки;
- benchmark на целевом CPU/RAM.

Базовые runtime-параметры:

```text
context: 8192
threads: 8
parallel: 1
max tokens: 768
temperature: 0.2
top_p: 0.8
top_k: 20
```

На этом этапе не добавлять:

- embeddings;
- Wiki.js ingestion;
- retrieval;
- vector DB;
- RAG endpoint;
- provider abstraction;
- Web UI.

Результат этапа: приложение имеет проверенный локальный CPU LLM runtime, готовый к дальнейшему использованию в RAG.

## 3. `wikijs-markdown-ingestion`

### Brief для OpenSpec

Создать change `wikijs-markdown-ingestion`.

Цель: реализовать получение Markdown-документации из Wiki.js в локальный ingestion pipeline.

Нужно обеспечить получение исходного Markdown и необходимых метаданных страниц в форме, пригодной для последующих этапов chunking и indexing.

Система остаётся read-only по отношению к Wiki.js.

На этом этапе не добавлять:

- embeddings;
- semantic retrieval;
- keyword/hybrid retrieval;
- vector DB;
- RAG chat endpoint;
- Web UI;
- автоматическую генерацию ответов.

Результат этапа: приложение умеет воспроизводимо получить и нормализовать Markdown-документы Wiki.js для последующей обработки.

## 4. `rag-evaluation-corpus`

### Brief для OpenSpec

Создать change `rag-evaluation-corpus`.

Цель: подготовить небольшой фиксированный evaluation corpus для проверки качества будущего RAG.

Нужно определить набор реальных вопросов по документации и ожидаемые страницы/фрагменты-источники, которые должны находиться retrieval-системой.

Corpus должен быть воспроизводимым и пригодным для сравнения разных вариантов chunking и retrieval.

На этом этапе не требуется реализовывать полноценный RAG endpoint или пользовательский интерфейс.

Результат этапа: есть фиксированный набор тестовых вопросов и ожидаемых источников, по которому можно объективно проверять следующие этапы.

## 5. `markdown-chunking`

### Brief для OpenSpec

Создать change `markdown-chunking`.

Цель: реализовать детерминированное разбиение Markdown-документов на chunks для последующего поиска.

Chunking должен учитывать структуру Markdown и сохранять достаточный контекст и метаданные источника, чтобы найденный fragment можно было связать с исходной страницей и использовать для цитирования.

Нужно корректно работать как минимум с:

- заголовками;
- обычным текстом;
- code blocks;
- bash-командами;
- таблицами;
- большими Markdown-страницами.

На этом этапе не подключать embeddings и retrieval.

Результат этапа: каждый исходный Markdown-документ воспроизводимо преобразуется в набор chunks с необходимыми метаданными.

## 6. `sqlite-index-storage`

### Brief для OpenSpec

Создать change `sqlite-index-storage`.

Цель: добавить локальное хранение данных будущего RAG-индекса в SQLite.

Хранение должно поддерживать данные документов, chunks и необходимые служебные метаданные для последующих retrieval-этапов.

Не добавлять:

- отдельную vector database;
- Redis;
- PostgreSQL для RAG-индекса;
- внешние сервисы хранения;
- фоновые очереди.

Результат этапа: данные ingestion/chunking можно локально и воспроизводимо сохранять и читать из SQLite.

## 7. `semantic-retrieval`

### Brief для OpenSpec

Создать change `semantic-retrieval`.

Цель: реализовать локальный semantic retrieval по chunks.

Планируемая embedding-модель:

```text
multilingual-e5-small
```

Embedding-модель должна:

- устанавливаться заранее;
- работать локально;
- не скачиваться во время runtime;
- поддерживать русский текст.

Нужно реализовать получение embeddings, сохранение необходимых данных и поиск наиболее релевантных chunks по пользовательскому вопросу.

Не добавлять отдельную vector DB без отдельного обоснования.

Результат этапа: по вопросу пользователя система возвращает релевантные chunks на основе semantic similarity.

---

## 8. `lexical-and-hybrid-retrieval`

### Brief для OpenSpec

Создать change `lexical-and-hybrid-retrieval`.

Цель: добавить lexical/keyword search и объединить его с semantic retrieval.

Hybrid retrieval должен использовать как минимум:

- semantic similarity;
- lexical/keyword relevance.

Результаты должны проверяться на `rag-evaluation-corpus`.

Не добавлять reranker на этом этапе, если отдельные измерения не покажут его необходимость.

Результат этапа: система возвращает итоговый набор chunks на основе hybrid retrieval, а качество можно сравнить с чистым semantic retrieval.

---

## 9. `atomic-full-reindex`

### Brief для OpenSpec

Создать change `atomic-full-reindex`.

Цель: реализовать безопасную полную переиндексацию документации.

Новый индекс должен строиться отдельно от текущего активного состояния и становиться активным только после успешного завершения полного процесса ingestion → chunking → indexing.

При ошибке существующий рабочий индекс должен сохраняться.

Не добавлять фоновые очереди или распределённую инфраструктуру без отдельной необходимости.

Результат этапа: полная переиндексация не оставляет систему в частично обновлённом или повреждённом состоянии.

## 10. `grounded-chat-api`

### Brief для OpenSpec

Создать change `grounded-chat-api`.

Цель: реализовать первый полноценный RAG API поверх retrieval и локальной LLM.

Поток обработки:

```text
вопрос
→ retrieval
→ найденный контекст
→ локальная LLM
→ grounded answer
→ sources / citations
```

Обязательные требования:

- ответ строится на найденном контексте;
- ответ содержит источники и цитаты;
- источники должны быть связаны с исходными документами/chunks;
- если найденных данных недостаточно, модель не должна додумывать ответ;
- LLM остаётся доступна только внутри Compose network;
- RAG остаётся read-only.

Не добавлять Web UI на этом этапе.

Результат этапа: появляется минимальный API вопрос → grounded answer → sources.

---

## 11. `session-follow-up`

### Brief для OpenSpec

Создать change `session-follow-up`.

Цель: добавить поддержку follow-up вопросов в рамках пользовательской сессии.

Система должна уметь учитывать необходимый контекст предыдущего диалога, когда новый вопрос зависит от предыдущего.

При этом нельзя бесконтрольно добавлять всю историю разговора в prompt.

Нужно определить минимальный и предсказуемый механизм работы с session context.

Результат этапа: пользователь может задавать связанные уточняющие вопросы без потери контекста и без неконтролируемого роста prompt.

## 12. `minimal-web-ui-and-health`

### Brief для OpenSpec

Создать change `minimal-web-ui-and-health`.

Цель: добавить минимальный Web UI для работы с RAG и необходимые эксплуатационные health/status проверки.

Web UI должен позволять:

- задать вопрос;
- увидеть ответ;
- увидеть источники/цитаты;
- увидеть понятную ошибку при недоступности необходимых компонентов.

Не превращать этот этап в отдельный сложный frontend-проект.

Результат этапа: RAG можно использовать через простой локальный Web UI, а состояние основных компонентов можно диагностировать.

## 13. `offline-mvp-acceptance`

### Brief для OpenSpec

Создать change `offline-mvp-acceptance`.

Цель: провести финальную интеграционную приёмку локального read-only RAG MVP на целевом сервере.

Проверить полный сценарий:

```text
Wiki.js
→ ingestion
→ chunking
→ local storage
→ embeddings
→ semantic + lexical/hybrid retrieval
→ grounded generation
→ citations
→ Web UI / API
```

Необходимо подтвердить как минимум:

- запуск после предварительной установки без внешнего интернета;
- отсутствие runtime-загрузок моделей;
- получение данных из Wiki.js;
- корректный chunking;
- локальное хранение индекса;
- semantic retrieval;
- lexical/hybrid retrieval;
- безопасную полную переиндексацию;
- grounded answers;
- обязательные источники и цитаты;
- корректный отказ от ответа при недостатке данных;
- session follow-up;
- Web UI;
- app/LLM health;
- отсутствие необязательной инфраструктуры;
- приемлемую работу на целевом CPU/RAM.

Результат этапа: подтверждён полностью локальный read-only RAG MVP, соответствующий `SPEC.md`.
